- [ ] **R1 — Customer email quota race and off-by-one:** reserve confirmation eligibility atomically across distinct leads, including one address per 24 hours and the exact hourly limit. Prove concurrent requests and the boundary. Customer emails remain off.

- [ ] **R8 — Ambiguous email failure can duplicate reminders:** use stable provider idempotency and prove that accepted mail with a lost response is not delivered twice on retry. Document uncertain-delivery handling.

- [ ] **R10 — Incorrect landing-page sharing-image dimensions:** emit metadata that agrees with the rendered image dimensions; verify all affected landing pages.

These requirements apply before PR #55 starts persisting enquiries, even if the staff pages and customer emails remain disabled. They are not postponed to Phase 2.

- [ ] **Disclosure:** review and approve the public description of the lead store, its purposes, stored contact/free-text/skin-goal/attribution data, providers and access. Include appointment/revenue/notes fields before those are used. The production site at the reviewed revision has no deployed cockpit/D1 ingestion; do not describe planned storage as already live.
- [ ] **Retention and deletion:** agree who owns the data, a justified retention period, how requests to correct/delete data are handled, and a tested deletion/anonymisation procedure covering leads and related events. The old plan's 24-month value is a proposal, not an implemented policy. Retention implementation and policy selection are outside this repair batch and remain launch blockers.
- [ ] **D1 failure alerting:** assign an agency owner and define a monitored log/alert route for `Lead ingest failed` and storage outages, including response time and escalation. Logging alone is not an alert. Configure and test this before rollout; this document does not claim an alert exists.
- [ ] **Lead reconciliation:** define a regular comparison of accepted enquiry emails against stored leads using arrival time, source and contact details. A D1 error intentionally allows the owner email to succeed; the cockpit can therefore miss an accepted enquiry. Define a secure manual recovery path and audit note, and a separate way to record WhatsApp enquiries. Manual-entry software is not implemented by this repair.
- [ ] **Recovery and rollout:** verify migration permissions, backups/recovery, agency-only access and test exclusions; document the approved rollout and rollback sequence. Database creation recorded in the handover does not prove current contents or readiness.

Until these gates are met, cockpit totals must not be represented as a complete record of enquiries. Compare actual notifications/outcomes rather than equating Pixel events or Treatwell clicks with bookings.
